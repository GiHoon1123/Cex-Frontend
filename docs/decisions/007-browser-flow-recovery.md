# 실제 브라우저 사용자 흐름 복구와 거래 화면 정리

고객 회원가입, 자체 BTC 차트, 주문·취소, 운영자 최초 보안키 등록을 실제 Chrome과 로컬 전체 스택으로 검증했다. 화면만 렌더링하는 검증과 엔진·Kafka·플랫폼을 통과한 금융 흐름을 구분해 기록한다.

## 문제와 기존 동작

- 회원가입 화면은 비밀번호 6자를 허용했지만 플랫폼은 유니코드 코드 포인트 15자 이상을 요구했다. 화면 검증을 통과한 요청이 플랫폼에서 거부됐다.
- 운영자 화면은 이미 등록한 보안키의 서명만 지원했다. 별도 관리 프로세스가 발급한 일회성 등록 비밀을 입력하고 최초 보안키를 등록할 화면이 없었다.
- WebAuthn 등록 결과를 인증 서명과 같은 JSON으로 보냈다. 플랫폼 표준 검증기는 장치 이름과 `credential`을 묶은 등록 봉투를 요구하므로 실제 Chrome 등록이 거부됐다.
- 반환값이 없는 운영자 등록 API의 `200` 빈 본문을 JSON으로 읽어, 서버 등록 성공을 화면 실패로 바꿨다.
- 데스크톱 전체를 80%로 축소해 큰 여백이 생겼고 파란색 CTA와 밝은 회색 패널이 합의한 바이낸스 다크 기준과 달랐다.
- 자체 체결이 없으면 차트가 비어 있었다. 이는 외부 시세를 임의로 섞지 않는 올바른 데이터 경계지만, 전체 스택 검증에 실제 자체 체결 자료가 없어 차트 동작을 확인할 수 없었다.

## 기존 제품과 공식 자료의 접근

- [Binance BTC/USDT 현물 거래 화면](https://www.binance.com/en/trade/BTC_USDT?type=spot)의 검은 배경, 얇은 구획선, 노란 주요 행동, 녹색 매수·빨간 매도와 정보 밀도를 화면 기준으로 삼았다. 로고나 화면을 복제하지 않고 이미 합의한 시각적 관례만 적용했다.
- [Web Authentication Level 3](https://www.w3.org/TR/webauthn-3/)의 등록 `create()`와 인증 `get()`을 별개 절차로 유지했다. 브라우저가 만든 공개키 자격 증명을 플랫폼의 Spring Security 검증기에 전달하며 개인키를 애플리케이션 코드에서 다루지 않는다.
- 플랫폼 비밀번호 정책을 프론트에 그대로 반영하되, 서버 검증을 권위로 유지했다. 프론트 검증은 사용자 피드백이고 보안 경계가 아니다.

## 선택과 트레이드오프

외부 거래소 봉을 넣으면 첫 화면을 즉시 채울 수 있지만 자체 엔진 체결과 외부 체결의 의미가 섞인다. 자체 체결만 표시하는 기존 결정을 유지하고 실제 고객 두 명의 교차 주문으로 차트 경로를 검증했다. 따라서 신규 로컬 DB는 최초 체결 전까지 빈 차트를 정직하게 표시한다.

운영자 최초 등록을 로그인 폼에 선택 입력으로 두면 별도 등록 화면보다 단순하다. 대신 평상시 로그인에도 필드가 보이는 비용이 있다. 현재 요구사항을 충족하는 최소 화면으로 선택했고, 빈 값이면 기존 보안키 인증만 수행한다.

색상과 레이아웃은 공통 테마 추상화를 새로 만들지 않고 현재 두 앱의 작은 범위에 직접 적용했다. 중복 색상 값이 남지만 아직 세 번째 소비자가 없고, 추측성 디자인 시스템을 추가하지 않는 이점이 더 크다.

## 구현과 관련 코드

[비밀번호 정책](../../apps/exchange/src/lib/password.ts)의 일부다.

```ts
if (Array.from(password).length < 15) {
  return { valid: false, message: '비밀번호는 15자 이상이어야 합니다.' };
}
```

`String.length`만 사용하지 않고 `Array.from`으로 코드 포인트를 센다. 플랫폼 Java의 `codePointCount`와 같은 기준으로 이모지를 한 글자로 다룬다. 최대 256 UTF-16 코드 단위, 제어 문자와 잘못 짝지은 서로게이트도 플랫폼과 같이 거부한다.

[WebAuthn 공통 변환](../../packages/ui/src/webauthn.ts)의 등록 봉투다.

```ts
export function registrationJson(credential:Credential,label:string):unknown {
  if(!label.trim()||label.length>100)throw new Error('보안키 이름은 1자 이상 100자 이하여야 합니다');
  return {credential:credentialJson(credential),label};
}
```

등록은 공개키와 장치 이름을 묶고, 이후 인증은 `credentialJson`의 서명만 보낸다. 실제 Chrome 가상 인증기로 등록과 별도 서명을 연속 수행해 이 차이를 확인했다.

[운영자 화면](../../apps/admin/src/app/page.tsx)은 비밀번호 로그인 후 일회성 등록 비밀이 있으면 `navigator.credentials.create()`로 최초 키를 등록한다. 등록만으로 운영 API를 열지 않고 다시 `navigator.credentials.get()` 서명을 요구한다. [운영 API 클라이언트](../../apps/admin/src/lib/api.ts)는 `200` 빈 본문과 `204`를 모두 성공으로 처리한다.

[거래 화면](../../apps/exchange/src/app/page.tsx)은 80% 축소를 제거하고 자산, 차트·주문, 호가·체결의 세 영역이 전체 폭을 사용한다. [차트](../../apps/exchange/src/components/MarketChart.tsx)는 자체 1분 봉만 그리며 `#0b0e11`, `#f0b90b`, `#0ecb81`, `#f6465d` 계열로 주요 화면을 통일했다.

## 작성한 테스트

- `tests/contracts.test.ts`
  - `회원가입 비밀번호를 플랫폼과 같은 유니코드 기준으로 검증한다`: 14/15자 경계, 이모지, 제어 문자, 잘못 짝지은 서로게이트, 최대 길이를 검증한다.
  - `플랫폼의 포괄적인 영문 오류를 고객이 이해할 한국어로 표시한다`: 400·403·503 변환과 구체적인 한국어 사유 보존을 검증한다.
  - `보안키 등록은 서명과 다른 표준 등록 봉투로 보낸다`: 장치 이름과 자격 증명 묶음 및 빈 이름 거부를 검증한다.
- `e2e/admin.spec.ts`
  - `최초 등록 비밀로 보안키를 등록한 뒤 별도 서명으로 로그인한다`: `create()`와 `get()`이 모두 실행되고 운영 화면이 열리는지 검증한다.
- 기존 `e2e/exchange.spec.ts` 6개 시나리오를 다시 실행해 자체 호가·체결·차트, 결과 불명 주문, 큰 주문 ID, ETH 시장, 마이페이지 회귀를 확인했다.

## 실행 명령과 결과

자동화 검증은 Node 22와 설치된 Chrome에서 실행했다.

```text
npm test          17 통과, 실패 0
npm run lint      고객·운영 앱 통과
npm run build     고객·운영 앱 통과
npm run test:e2e  8 통과, 실패 0
```

실제 로컬 전체 스택은 PostgreSQL `5433`, 격리 Kafka `19092`, 엔진 `3002`, 플랫폼 `8080`, 고객 `3003`, 어드민 `3004`를 사용했다. 봇은 0명으로 유지했다.

- Chrome에서 새 고객 회원가입·로그인 성공
- 서로 다른 두 고객이 BTC 0.01을 60,000 USDT에 매도·매수해 실제 엔진 체결 성공
- Kafka 소비 뒤 자체 체결 1분 봉, 최근 체결, 잔액·평균 매수가 표시 성공
- 50,000 USDT 미체결 주문 생성 후 취소 의도·엔진 확인·화면 제거 성공
- 거래내역과 마이페이지 이동, BTC/ETH 탭 전환 성공
- Didit·체인 노드를 끈 상태에서 KYC와 입금 주소 발급이 성공으로 가장되지 않고 한국어 준비 불가 상태를 표시
- 비웹 관리 프로세스로 새 운영 계정을 부여한 뒤 Chrome 가상 인증기로 최초 보안키 등록, 별도 서명, 운영 상태·승인·시장감시·감사 조회, 로그아웃 성공

자체 체결 검증을 위해 이번 작업이 만든 로컬 전용 엔진 저널 파일만 삭제하고 초기 잔액에서 다시 부트스트랩했다. 이 테스트 저널은 복구 대상 운영 자료가 아니며 삭제 후 복구할 수 없다. 기존 `cex` DB와 기존 Kafka는 변경하지 않았다.

외부 Didit 자격증명, Bitcoin 노드, Ethereum 노드를 켜지 않았으므로 실제 외부 KYC와 체인 입출금 성공은 이번 브라우저 검증 범위가 아니다. 화면은 이를 완료로 표시하지 않는다.
