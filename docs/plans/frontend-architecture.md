# 고객 거래소·어드민 프론트 설계 기준

바이낸스 다크 화면을 디자인 기준으로 삼고, 고객 거래소와 어드민을 기존 `Cex-Frontend` 저장소 안의 두 앱으로 구성한다. 모노레포의 경계, 공유 범위, 인증·API 계약과 구현 순서를 정한다.

- 작성일: 2026-10-21.
- 상태: 설계 기준과 구현 계획. 모노레포 전환·어드민 구현·배포는 아직 수행하지 않았다.
- 독자: TypeScript 백엔드를 주력으로 하며 프론트 설계·운영 판단을 설명하려는 프로젝트 소유자.

## 확정한 방향과 세부 제안

| 구분 | 기준 |
|---|---|
| 사용자 지정 | 바이낸스 다크 화면을 벤치마크하고 로고·아이콘까지 참고 범위에 포함한다 |
| 사용자 지정 | 고객 거래소와 어드민을 프론트 모노레포에서 함께 관리한다 |
| 사용자 지정 | 두 프론트를 엔진·플랫폼·DB·Kafka와 함께 초기 EC2 한 대에 배포한다 |
| 설계 제안 | 고객·어드민을 각각 실행·빌드·배포할 수 있는 Next.js 앱으로 구성한다 |
| 설계 제안 | 기존 npm을 유지하고 npm workspaces로 구성한다 |
| 설계 제안 | 공통 UI를 먼저 공유하고 업무 로직은 각 앱 안에서 관리한다 |

## 현재 코드에서 확인한 출발점

2026-10-21의 정적 확인 기준이다. 동작·보안 검증 결과를 뜻하지 않는다.

- [package.json](../../package.json): Next.js `16.0.8`, React `19.2.0`, TypeScript, Tailwind CSS 4와 npm lockfile 사용.
- [앱 디렉터리](../../src/app/): 기존 고객 화면은 App Router 기반이며 어드민 앱은 없다.
- [API 클라이언트](../../src/lib/api.ts): 엔진 연결과 브라우저 `localStorage` 토큰 저장 경로가 있다.
- [Next.js 설정](../../next.config.ts): 운영 프록시와 기존 엔진 주소 기본값이 있다.
- [주문장](../../src/components/OrderBook.tsx), [체결 내역](../../src/components/TradeHistory.tsx): 바이낸스 외부 시세 연결이 있다.
- `package.json`에 테스트 실행 스크립트나 전용 테스트 라이브러리는 선언돼 있지 않다. 도구 선정 시 기존 테스트 파일·전이 의존성·공식 문서를 추가 확인한다.

구현 착수 시 현재 코드와 다시 대조한다. 이 목록을 근거로 기존 동작을 검증했다고 표시하지 않는다. 모노레포 전환 후에는 이 문서의 코드 경로도 함께 갱신한다.

## 모노레포 구조

다음은 목표 구조다. 현재 존재하는 디렉터리와 혼동하지 않는다.

```text
Cex-Frontend/
├── apps/
│   ├── exchange/       # 고객 거래소 Next.js 앱
│   └── admin/          # 운영자 Next.js 앱
├── packages/
│   └── ui/             # 디자인 기준·로고·아이콘·기본 컴포넌트
├── docs/
├── package.json        # private workspace 루트
└── package-lock.json   # 공통 의존성 잠금
```

각 앱 안에서 라우트, 화면과 기능별 모듈을 나눈다. 화면에서 API 호출·형식 변환·실시간 연결·권한 판단을 모두 직접 처리하지 않도록 책임을 분리한다.

현재 npm을 유지하면 패키지 관리자를 바꾸는 비용 없이 작업 공간을 구성할 수 있다. npm은 루트에서 여러 workspace 패키지를 관리하는 기능을 제공한다. 빌드 캐시·실행 순서 관리 도구는 실제 요구가 생길 때 비교한다. [npm workspaces 공식 문서](https://docs.npmjs.com/cli/v11/using-npm/workspaces/)

**트레이드오프:** 두 앱은 단일 앱의 `/admin` 경로보다 빌드·설정이 늘어난다. 고객·운영자 접근 경로와 배포를 독립적으로 관리할 수 있다. 저장소·컨테이너 분리만으로 권한이나 호스트 침해 격리가 완성되지는 않는다.

## 디자인 기준

참고 제품은 [바이낸스 현물 거래 화면](https://www.binance.com/en/trade/BTC_USDT?type=spot)이다. 다크 화면을 기준으로 디자인 선택을 줄이고 업무 구현에 집중한다.

| 항목 | 구현 전에 고정할 내용 |
|---|---|
| 색상 | 배경·패널·경계선·텍스트·강조·상승·하락 |
| 타이포 | 글자 크기·굵기·줄 높이, 가격·수량의 숫자 정렬 |
| 고객 배치 | 헤더·차트·주문장·주문 입력·주문 내역 |
| 공통 요소 | 버튼·입력·탭·표·모달·상태·알림 |
| 로고·아이콘 | 참조 화면, 실제 사용할 파일, 출처, 이름과 사용 위치 |
| 반응형 | 고객 데스크톱·모바일, 어드민 데스크톱 우선 |

디자인 구현 사이클에서 참조 화면과 확인일을 고정한다. 정확한 색상·크기·아이콘 파일을 아직 측정·수집하지 않았으므로 이 문서에서 임의 수치를 확정하지 않는다. 거래소 이름과 실제 노출할 로고 파일은 자산 목록에서 결정한다.

어드민은 같은 스타일의 목록 → 상세 → 심사·승인 흐름을 사용한다. 로고·아이콘·디자인 값은 `packages/ui`에서 관리한다. 색상과 함께 상태 문구를 표시하고 키보드 조작·포커스·입력 오류 안내를 제공한다.

**트레이드오프:** 제품 기준을 고정하면 화면 제작과 일관성 관리가 빨라진다. 우리 서비스가 지원하는 주문·심사 상태에 맞춰 정보 배치를 조정해야 한다.

## 공통 코드와 앱별 업무

| 공유 대상 | 앱 안에 둘 대상 |
|---|---|
| 디자인 값, 로고·아이콘 | 고객 주문·취소·자산 업무 |
| 버튼·입력·탭·모달·기본 표 | 운영자 심사·승인·조사 업무 |
| 상태·오류·로딩 표시 | 앱별 세션·권한과 API 연결 |

API 타입·금액 표시 함수도 양쪽 앱에서 실제로 사용하는 시점에 추출한다. 사용자와 운영자 인증을 하나의 전역 상태나 토큰 저장소로 합치지 않는다.

**트레이드오프:** 초기에 일부 반복이 생길 수 있다. 아직 다른 업무를 공통화하기 위해 옵션·분기·범용 계층을 늘리는 일을 줄인다.

## 인증과 API 계약

- 고객·운영자 업무는 플랫폼 API를 통해 처리한다. 브라우저가 내부 엔진 명령 API를 직접 호출하지 않는다.
- 거래소와 어드민에 별도 로그인·세션 경계를 둔다. 고객 세션으로 운영자 업무를 실행할 수 없어야 한다.
- 앱마다 호스트 범위의 쿠키를 사용하고 부모 도메인 공유 쿠키를 피하는 방향을 검토한다. 쿠키 이름·경로만으로 서버 인가를 대신하지 않는다.
- 브라우저 세션은 `HttpOnly`·운영 HTTPS의 `Secure`·적절한 `SameSite`와 CSRF 검증을 함께 설계한다. 기존 토큰 저장 경로는 새 세션 계약 완성 시 제거한다.
- 동일 출처 `/api` 경로를 기본 제안으로 삼는다. 쿠키 발급·API 프록시 담당은 플랫폼 계약과 함께 확정하고, 단순 전달을 위해 불필요한 인증 서버를 추가하지 않는다.
- Next.js는 세션 확인·표시를 담당하고, 플랫폼은 모든 요청의 업무 권한과 고객 제한·승인을 최종 검증한다.
- 금액·수량은 정밀도를 보존하는 API 표현과 검증·반올림 규칙을 정한다. JavaScript `number`의 계산 결과를 금융 확정 근거로 사용하지 않는다.
- 요청 실패, 업무 거절, 처리 결과 불명을 구분한다. 주문·출금에 무조건 자동 재시도를 적용하지 않는다.
- 자체 주문장·체결을 연결하고 외부 시세는 참고 데이터로 구분한다.
- 실시간 데이터는 스냅샷·변경분 순서, 누락·재연결·재동기화를 관리한다. 같은 데이터의 중복 연결과 숨겨진 화면의 중복 조회를 줄인다.
- 고객·운영자 응답이 다른 세션에 캐시돼 노출되지 않도록 사용자별 데이터와 캐시 경계를 검증한다.

Next.js 공식 가이드는 인증·세션·인가를 구분한다. 기존 플랫폼 인증을 확인하고 역할을 정하며 프론트에 별도 고객 DB·비밀번호 검증을 중복 구현하지 않는다. [Next.js 인증 가이드](https://nextjs.org/docs/app/guides/authentication)

**트레이드오프:** 쿠키 기반 동일 출처 연결은 브라우저 토큰 노출과 CORS 구성을 줄일 수 있다. CSRF, 쿠키 범위, 프록시와 백엔드 변경을 함께 처리해야 한다.

## 고객·어드민 첫 화면 범위

| 고객 거래소 | 어드민 |
|---|---|
| 로그인·가입·계정 복구 | 운영자 로그인·필요한 추가 인증 |
| 고객 확인 시작·진행·심사 결과 | 고객 확인 목록·상세·조치 이력 |
| 주문장·차트·주문·체결·취소 | 업무별 대기 목록·심사·승인 |
| 자산·입출금·보안 설정 | 대사·이상거래·감사 조회를 순차 추가 |

KYC는 [Didit 검토 문서](../../../docs/roadmap/didit-kyc.md)의 호스팅 화면 연동을 초기 후보로 삼는다. 완료 페이지의 URL 파라미터로 고객 확인을 승인하지 않고 플랫폼이 검증한 상태를 표시한다. Didit 결과와 우리 거래소의 최종 이용 허용 판단을 구분한다.

## 구현 순서와 완료 조건

| 사이클 | 결과 | 완료 조건 |
|---|---|---|
| 1 | workspace 구성과 두 앱 실행 | 기존 고객 거래 화면 유지, 어드민 독립 실행·빌드, 공통 UI 참조 |
| 2 | 다크 디자인 기준·기본 컴포넌트 | 참조 화면·자산·반응형·키보드 동작 확인 |
| 3 | 고객 로그인·보호 화면 | 실제 플랫폼 세션 연결, 만료·로그아웃·타인 접근 테스트 |
| 4 | 운영자 로그인·권한 | 고객 세션·권한 없는 운영자 요청 차단 |
| 5 | 고객 확인 전체 흐름 | Didit 테스트 연동, 결과 반영·심사·이력과 고객 화면 연결 |
| 6 | 실제 거래 흐름 | 주문·체결·취소·자산 조회, 실패·중복·결과 불명 처리 |

전환할 때 기존 화면을 동작하는 앱으로 옮긴 뒤 필요한 기능을 추가한다. 쓰이지 않는 경로는 참조 확인 후 삭제하며 호환용 앱·프록시를 병행 유지하지 않는다.

## 작성할 테스트와 이번 작업 범위

향후 구현에서 컴포넌트 검사와 브라우저 전체 흐름 검사를 나눠 작성한다. 아래는 계획이며 테스트 파일·함수·명령은 도구 선정과 구현 후 기록한다.

- 로그인 성공·실패, 세션 만료·회수와 로그아웃.
- 고객·운영자 세션 격리, 직접 URL·API 접근과 권한 상승 차단.
- 승인 대상 변경·중복 제출·API 실패·처리 결과 불명.
- 금액 정밀도·입력 경계와 상태 표시.
- 실시간 중복·누락·재접속·페이지 이동 후 연결 정리.
- KYC 복귀 URL 조작, 심사 대기·거절·재제출과 외부 장애.
- 주요 화면 크기, 키보드·포커스·오류 안내와 시각적 회귀.

이번 작업은 문서 작성이다. 신규 테스트 코드를 작성하지 않았으며 제품 테스트·빌드·실행·배포는 수행하지 않았다. 기존 `src/`, 패키지·실행 설정과 서비스는 변경하지 않았다.
